# Airtable import

Moves **Vision Admin V2 (Jah Copy)** — `appEobvB14kpW8hHw` — into the app.

Read `docs/AIRTABLE-MIGRATION.md` first for the reasoning. This is the runnable
part.

> **Before you run anything, confirm which schema your Supabase database
> actually has.** The repo contains two migrations that both create the Vision
> schema, and they disagree. `00-preflight.sql` tells you which one is live and
> whether the import can proceed. See "Preflight" below.

## What it does

```
extract.mjs        Airtable  →  airtable-export/00-data.sql   (raw JSON, record IDs kept)
01-staging.sql     creates the staging schema
00-data.sql        loads the raw records into staging
02-transform.sql   staging   →  live tables, in dependency order
03-verify.sql      read-only reconciliation
```

Nothing is transformed during extraction. The raw records land in `staging` as
`jsonb` so a surprise value is never silently dropped, and the transform can be
re-run and inspected without going back to Airtable.

## Running it

```sh
# 1. Preflight — does the live schema support the import?
psql "$DATABASE_URL" -f scripts/airtable-import/00-preflight.sql

# 2. Extract. Token needs data.records:read + schema.bases:read on the base.
AIRTABLE_PAT=pat... node scripts/airtable-import/extract.mjs

# 3. Load and transform
psql "$DATABASE_URL" -f scripts/airtable-import/01-staging.sql
psql "$DATABASE_URL" -f airtable-export/00-data.sql
psql "$DATABASE_URL" -f scripts/airtable-import/02-transform.sql

# 4. Check
psql "$DATABASE_URL" -f scripts/airtable-import/03-verify.sql
```

`DATABASE_URL` is the Supabase connection string from
Project Settings → Database → Connection string → URI.

**Run it against a branch or a copy first, never straight at production.**

## It is re-runnable

Every insert is keyed on `airtable_id` and ends with `on conflict do nothing`,
and the whole transform is one transaction. Run it, find something wrong in
Airtable, fix it, re-extract, run it again — you get the same result, not
duplicates. Verified over three consecutive runs.

That matters at cutover: you will run it at least twice — once to rehearse, once
for real after Airtable is frozen.

## What is deliberately left behind

| Not migrated | Why |
|---|---|
| Billing rows with status `Draft` or blank | Half-filled records; no equivalent status. Re-create in Class Builder |
| Sessions with no scheduled start or end | `session_times_ordered` would reject them |
| Charges whose Hours or Attendance link does not resolve | `charge_one_source` needs exactly one source |
| Everything Airtable computed | Every `Validation Flag`, `… Count`, `… Candidate`, `… - Lookup`, `Hours Used`, `Hours Remaining`, `Final Amount`, `Make-up State`, `Hours to Consume` — all are views now |
| Automation plumbing | `Hours Creation *`, `Charge Creation *`, `Retry *`, `Activation *`, `Generate Sessions` |
| `Students.Gender`, `Students.Exam Targets` | No column in the schema. Ask and I will add them |

Section 2 of `03-verify.sql` lists every skipped row with its reason, so nothing
disappears quietly.

## Codes

Codes are **not** carried across — they are generated by the database. Rows are
inserted in a deterministic order so `STU-`, `GUA-`, `TUT-`, `HRS-`, `SES-`,
`ATT-` and `CHG-` come out matching Airtable. Class Offerings and Billing are
renumbered (`OFF-2026T3-…` → `OFF-0001`, `BILL-nnnn` → `ENR-nnnn`), which was
agreed — the offering codes were a mix of two formats and are now consistent.

The originals are kept in `airtable_id` on every row, forever.

## What was tested

The transform runs against a real Postgres 16 with the spec schema and fixtures
shaped exactly like the Jah Copy. Confirmed:

- Sibling sharing one guardian; two guardians on one student; default payer set
  through the deferred trigger
- Draft billing excluded; a session with no start time excluded; a charge with
  no source excluded — each reported with its reason
- Private tuition capacity forced to 1 regardless of what Airtable said
- One package eligible across two enrolments (the case the roll depends on)
- Hour consumption: present regular consumes, trial consumes nothing, and a
  present roll entry on a **cancelled** lesson consumes nothing
- A make-up promoted with its source link set in the same statement, and its
  absence correctly reading `completed`
- A make-up whose source did not survive demoted to regular with a note
- Cancelled and rescheduled lessons pay zero; the replacement carries the pay
  adjustment; the tutor rate applies from before the earliest lesson
- Three consecutive runs producing identical counts

Not tested against the real base — that needs a token, and it needs you to
decide the preflight question first.
