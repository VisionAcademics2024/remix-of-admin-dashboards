Leads & Trials

A pre-student pipeline that sits upstream of the existing chain. It captures an enquiry, records every time we reach out, and — on conversion — routes the family into a trial class or a bespoke diagnostic, then hands them off to a real student and enrolment.

3 new tables 6 new enums 1 view reuses students · enrolments · sessions RLS: is_staff()
01

Where it slots into the chain

The existing model starts at guardian → student. Leads live one step before that. A lead is contacted, may be booked into a trial or diagnostic, and only converts into a student + enrolment once they say yes — reusing the machinery that already exists rather than duplicating it.

04

Relationships & rules

How the new tables reach into the existing schema, and the constraints the database enforces so the pipeline can’t record a contradiction.

1·nleads → lead_contacts
Many touchpoints per lead. Deleting a lead cascades its contact log.
1·nleads → trials
A lead may be offered more than one trial (e.g. a diagnostic, then a class trial).
n·1trials → class_offerings / sessions
“Which trial class they’ll join.” Making a new trial class is just creating an offering and pointing here.
1·1leads → students / enrolments
On conversion the lead names the student it became and the trial enrolment that delivers it.
n·1trials → tutors / programs
Who ran the diagnostic, and the program it recommends.
CKlead_lost_needs_reason
Status lost requires a written lost_reason — mirrors the project’s “adjustments need a reason” stance.
CKlead_converted_needs_student
Status converted can’t be set without a converted_student_id.
CKtrial_class_needs_offering
A class_trial must point at a class offering; a diagnostic_test need not.
RLSis_staff() on all three
Operational data — any active staff member, full access. Added to the same policy loop the other 14 tables use.
TGset_updated_at()
The shared touch trigger on leads and trials, exactly as everywhere else.
05

The derived view

Facts stay in the tables; the working list the admin screen reads comes from a view, so “overdue”, “days since contact” and counts never drift.

v_leads

Each lead, enriched for the pipeline board — the latest contact, how long it’s been sitting, whether a promised follow-up is past due, and how many trials it’s spawned. security_invoker = true, like every other view.
