# 02 — Database Schema

Prose companion to `03-schema.sql`. The SQL is the source of truth; this explains the *why*,
which is the part a coding agent cannot infer.

---

## Design decisions worth not undoing

### Base tables store facts, views compute
There is no stored `hours_remaining`, no stored `pay`, no stored `validation_flag`. All of it
lives in views. Two reasons: derived values that are stored drift, and timezone-dependent maths
(`at time zone` is `stable`, not `immutable`) cannot legally be a Postgres generated column.

If a view becomes slow, materialise it — do not move the logic into a column.

### Codes are generated columns, not application logic
```sql
seq  bigint generated by default as identity,
code text generated always as ('STU-' || lpad(seq::text, 4, '0')) stored
```
The database owns the sequence. Codes cannot be typed, edited, duplicated or skipped by an app
bug. Numbers are never reused after a delete, which is correct — a deleted `STU-0031` must not
come back as someone else.

### Frozen values are real columns, not lookups
`enrolments.base_price`, `tutor_payouts.rate_at_payout`, `charges.standard_amount` are all copies
taken at the moment of agreement. Changing a catalogue price or a tutor's rate later must never
rewrite what was agreed or paid. This is the one place duplication is correct.

### Uniqueness constraints that eliminate whole bug classes

| Constraint | Prevents |
|---|---|
| `sessions (class_offering_id, starts_at)` unique | Duplicate lessons from re-running generation |
| `attendance (session_id, enrolment_id)` unique | The same student twice on one roll |
| `charges (attendance_id)` unique partial | Billing one lesson twice |
| `charges (package_id)` unique partial | Billing one package twice |
| `tutor_payouts (tutor_id, fortnight_start)` unique | Paying a fortnight twice |
| `enrolments (student_id, class_offering_id, starts_on)` unique | Duplicate enrolment |

Each of these was a live incident in the Airtable system, guarded only by a formula people could
ignore. Here the database refuses.

### Check constraints that encode business rules

- `charge_one_source` — a charge has exactly one hours package **or** exactly one attendance,
  never both, never neither.
- `charge_parent_needs_payer` — a parent-routed charge must name a payer.
- `charge_paid_needs_evidence` — status `paid` requires a date and a method.
- `payout_adjustment_needs_reason` — an adjustment without a written reason is rejected.
- `courtesy_is_free` — a courtesy package must have zero price and a stated reason.
- `private_capacity_one` — private tuition is capacity 1.
- `enrolment_method_required` — only a trial may omit a billing method.

### Two triggers for rules a check constraint can't express

- **Default payer must be a guardian of that student.** Deferred to the end of the transaction so
  a student and their guardian link can be inserted together.
- **A package may only be spent on an eligible enrolment, and must belong to the same student.**
  Runs on attendance insert/update.

## Table reference

### People

**`guardians`** — parents and payers. Never log in. `code` is `GUA-nnnn`.

**`students`** — `code` is `STU-nnnn`. `default_payer_id` is the person charges are billed to and
must also appear in `student_guardians`.

**`student_guardians`** — many-to-many. Siblings work by attaching the same guardian to several
students.

**`tutors`** — `code` is `TUT-nnnn`. `colour` is a hex string for the timetable. Note there is
**no rate column here** — see below.

**`tutor_pay_rates`** — *owner-only table.* One row per rate change, with `effective_from`.
Two jobs at once: it keeps rate history so past pay can be explained, and because it is a separate
table it can be hidden from non-owner staff by row-level security, which a column on `tutors`
could not be. If you only ever want one rate per tutor, just keep one row each.

### Catalogue

**`operating_periods`** — terms. `code` like `2026-T4`.

**`standard_prices`** — the versioned price list. `basis` drives everything downstream:

- `per_hour` — `quantity` is meaningless; the enrolment must set `hours_override`
- `per_session` — `quantity` is sessions in the block
- `fixed_hours_price` — `quantity` is hours in the block

Never edit an old price. Create a new row and set the old one `inactive`.

**`programs`** — the reusable catalogue of what is taught. No dates, no tutor.

### Classes and lessons

**`class_offerings`** — a program, in a term, with a tutor, a recurrence and a duration.
`recurrence_start` fixes both the weekday and the time of day that generation uses.

**`sessions`** — one lesson. Duration derives from `starts_at`/`ends_at`; there is no duration
column to fall out of step. `tutor_id` is per-lesson, which is how cover works.
`replaces_session_id` links a rescheduled lesson to the one it replaces.

**`session_pay_adjustments`** — *owner-only.* Zero or more adjustments per lesson, each with a
mandatory note. Kept out of `sessions` so that non-owner staff see no money at all on the
timetable.

### Enrolments and packages

**`enrolments`** — a student in a class for a date range, carrying frozen commercial terms.
`default_package_id` is which package new roll entries should draw from.

**`hours_packages`** — a block of purchased or courtesy hours belonging to one student.
Balance is computed in `v_hours_packages`, never stored.

**`package_eligibility`** — which enrolments a package may be spent on. A student in two classes
can share one package across both. This is the single most misunderstood relationship in the old
system; making it an explicit table rather than an implicit rule is deliberate.

### Attendance

**`attendance`** — one row per student per lesson. `att_type` of `trial` never consumes hours.
`source_attendance_id` points a make-up back at the absence it settles; make-up state is derived
from whether a linked attempt exists and whether it is present.

### Money

**`charges`** — one source, one charge. Discounts go in `adjustment` as a negative number.
`xero_invoice_no` lets several charges share one external invoice, which is how you bill a family
for a fortnight of PAYG lessons on one document while keeping per-lesson traceability.

**`tutor_payouts`** — *owner-only.* One row per tutor per fortnight, freezing hours and rate.

### Leads and trials

Added by `20260826120000_leads_trials.sql`. The pre-student pipeline — everything upstream
of a guardian and a student. Same conventions as everything else: uuid keys, a generated
`code`, `airtable_id`, a touch trigger, facts only.

**`leads`** — one enquiry. `code` is `LEAD-nnnn`. The child (`student_name`, `year_level`)
and enquiring parent (`guardian_name`, `guardian_email`, `guardian_mobile`) are free text
because no records exist yet. `status` drives the pipeline; `source` is categorical for
attribution. On conversion the row records `converted_student_id` and
`converted_enrolment_id`. Two check constraints: `lead_lost_needs_reason` (a `lost` lead
must say why) and `lead_converted_needs_student` (can't mark converted without the student
it became).

**`lead_contacts`** — the contact log, one row per touchpoint, with a mandatory `summary`
and an optional `next_action_on`. Cascades when its lead is deleted. Indexed
`(lead_id, contacted_at desc)` because it is always read newest-first.

**`trials`** — a booked trial or diagnostic for a lead. `code` is `TRL-nnnn`. `kind` is
`class_trial` (must name a `class_offering_id` — enforced by `trial_class_needs_offering`)
or `diagnostic_test` (carries a `recommendation`, `score` and `recommended_program_id`).
`class_offering_id`, `session_id` and `enrolment_id` reuse the existing machinery rather
than duplicating it. Cascades when its lead is deleted.

All three are gated by `is_staff()` like the other operational tables — no owner-only data
here.

## Views

| View | Adds |
|---|---|
| `v_sessions` | Sydney date, duration, payable hours, fortnight window, `is_today`, `is_this_fortnight` |
| `v_attendance` | Hours consumed, effective status, make-up state, student and billing method |
| `v_hours_packages` | Hours used, remaining, low and overdrawn flags |
| `v_enrolments` | Final agreed price after the adjustment rule |
| `v_charges` | Final amount |
| `v_session_pay` | Rate at the time of the lesson, base pay, adjustments, total — **owner-only in effect** |
| `v_tutor_fortnight_pay` | Per tutor per fortnight totals |
| `v_needs_attention` | Every exception in the system, as one queryable union |
| `v_leads` | Latest contact, days since contact, days in pipeline, contact and trial counts, an `is_overdue` flag, and the assigned staff and program-interest names |

All views are `security_invoker = true`, so they respect the caller's RLS rather than the view
owner's. This is what makes the pay views safely invisible to non-owners: the underlying rate and
adjustment tables return no rows, so pay computes as zero rather than leaking.

> If you want non-owners to be blocked outright rather than see zeroes, have the API layer refuse
> the request based on role instead of relying on empty results.

## Deliberate omissions

- **No soft-delete columns.** Closing is modelled by status enums that already exist. Add
  `deleted_at` only if you find a real need.
- **No audit log.** If you want one, add a generic `audit_events` table written by triggers, and
  do it before go-live rather than after.
- **No tutor login.** The `staff` roles are `owner` and `admin` only. Adding a `tutor` role later
  means a `staff.tutor_id` link and RLS that filters to their own lessons — the schema is shaped
  to allow it, but it is not built.
- **`year_level` is free text**, not an enum, because it changes and you will want to edit it
  without a migration.
